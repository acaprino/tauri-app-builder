# Data and privileges of new windows

Part of the tauri-native-desktop references: versions, scope and limits are in [guide.md](guide.md). Bracketed names are sources; their URLs are in [sources.md](sources.md).

Each WebView starts with its own JS context: closures, component state and DOM refs are not automatically shared. Proposal: separate the form fields from the container; keep a local draft; apply the change through the authoritative service/host the app already uses. For apps that are also web apps, use a desktop adapter for the container and a browser one for the in-page overlay that takes the window's place there, without duplicating domain or validation. [State management].

**Beware of custom commands:** registering `invoke_handler` is not enough to restrict them to capabilities. By default app commands are available to app-local windows/WebViews; use `AppManifest::commands` and explicit permissions when granularity is needed. Remote origins require explicit remote capabilities in corrected versions: Tauri 2.11.1 fixed remote custom-command ACL bypass and incorrect local-origin classification. Do not assume the same boundary on older lockfiles; check the security fixes in [guide.md](guide.md). Permissions of overlapping capabilities add up. Verify with denied calls from the secondary window, not just by reading JSON. [Capabilities], [AppManifest], [tauri CHANGELOG].

For each window define allowed local route, label, role, commands, payloads/events and lifetime. Do not put passwords, tokens or sensitive data in the query string. Bind session and caller in the shell backend (the app's native side, which creates the windows); an ID sent by the client alone does not authenticate a window. Application data keeps using the authentication the service already provides.

Separate JS contexts and command permissions do not partition browser storage. Before claiming that a secondary window cannot access credentials, identify their actual storage and which origins, profiles and data stores can reach cookies, localStorage and IndexedDB. Same-origin windows sharing a profile can share that data even when a native credential command is denied. If the product requires isolation, verify it with a negative storage-access test and the platform's supported controls; `data_directory` is not a universal WKWebView solution (`data_store_identifier` requires macOS 14+). Reuse the existing authentication owner; do not introduce separate profiles unless the required boundary calls for them. [WebView2 user data folders], [WebviewWindowBuilder].

Capabilities can restrict access to event commands such as listen/emit, but do not provide fine-grained authorization of event names or payloads; channels likewise need application-level authorization at their creation and use. Minimize payloads, target the destination and authorize reads through the authoritative backend. Broadcast is not a channel for secrets. For heavy streams, channels provide transport/ordering rather than a substitute for caller validation. [Calling frontend], [Core event permissions].

## Example: secondary window without credential access

If a command that reads credentials is reserved to the main window, do not grant it automatically to a settings window or a form. Compare two alternatives against the local architecture: a relay of typed operations to the existing transport in the main window, or a broker in the shell if the shell already owns transport/authentication. In the first case main keeps talking to the service; in the second the broker is reused without introducing another domain. A limited session issued by the service is another option only if the service already supports it or the change is within the authorized scope. These are architectural proposals, not features Tauri offers automatically.

Minimal relay contract: the caller's real role, the form session, the allowed operation and a validated payload; correlated response, readiness, timeout, cancellation and error if main is unavailable. Labels/sessions declared by the client alone do not authenticate the caller. If main stays hidden, do not base correctness on page timers; test delays, reconnection and closing. Do not turn the relay into a generic HTTP proxy or into new shell domain actions. Document every change to the project's already intentional boundaries.

## Alternative for trusted forms: a portal in a same-origin document

A trusted form can be rendered by the main window's UI tree into a same-origin document opened with `window.open`, using a portal in React or a similar framework. This still creates a second WebView with its own document and JS globals; the React tree, callbacks and existing transport remain owned by the opener, so those callbacks need no separate relay. Verify the Tauri `on_new_window`/`NewWindowResponse::Create` path and propagate the requested `window_features`, including the related view, configuration or environment required by that platform. Apply the [shared bootstrap](web-layer.md) to the new WebView. Test opener access, navigation rules, menu/popover destinations, and what happens when either window closes, reloads or crashes. This is a platform-specific alternative to prove, not a ready-made portable adapter. [WebviewWindowBuilder], [React createPortal].

This path **shares trust with the main window**: the accessible opener prevents treating the form as an isolation boundary. Do not use it for remote content or user scripts. A capability without permissions is not enough to prove IPC protocol isolation in a shared WebView2 environment: verify the caller observed on the Rust side and every IPC route. A stricter CSP in the host document can constrain its direct network access, leaving operations to the main window's callbacks; it does not isolate a same-origin document from its accessible opener.
