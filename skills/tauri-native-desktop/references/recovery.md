# Recovering from WebView failures

Part of the tauri-native-desktop references: versions, scope and limits are in [guide.md](guide.md). Bracketed names are sources; their URLs are in [sources.md](sources.md).

On Windows a failed navigation or renderer process can leave an engine error page or blank content. The app must recover failed main/subframe content; a browser-process exit invalidates its associated controls and requires their recreation. This does not apply to every subprocess exit: GPU and utility failures are normally recovered by WebView2. If browser accelerators are disabled, provide an app-owned route out of a failed page. [Process-related events].

Proposal; items 1 to 3 go through `with_webview` in the shared bootstrap ([web-layer.md](web-layer.md)), right after the window is built. The switch applies from the next navigation: a first load can fail before it takes effect. Combine this bootstrap with the bounded hidden-startup and native fallback contract in [frame.md](frame.md), so the first visible surface never exposes that engine page and a failed first load never leaves an indefinitely hidden app.

1. Disable the built-in error page with `IsBuiltInErrorPageEnabled = FALSE`. When disabled "a blank page is displayed", so the app must own the error/recovery surface: a native message or a page bundled in the app that explains the problem and offers retry. [ICoreWebView2Settings].
2. Handle `ProcessFailed` by kind and affected process group. `RENDER_PROCESS_EXITED` needs reload/recreation and recovery of persisted drafts; `FRAME_RENDER_PROCESS_EXITED` needs a policy for the affected frames. `BROWSER_PROCESS_EXITED` invalidates WebViews sharing that browser process, not necessarily every WebView in the app. Restart the app only after required native state is persisted and no background operation must survive; Rust in-memory state is lost on process restart. Otherwise rebuild affected windows in the same process, after the environment's `BrowserProcessExited` event when reusing its data folder (`environment()` cast to `ICoreWebView2Environment5`; this integration is not compiled here). Subscribe to and coordinate both events before failures occur; their delivery order is not guaranteed. An unresponsive renderer may still hold unsaved work: offer recovery using the save contract below. Log other kinds and follow their documented recovery requirements. Add a bounded retry policy and app-owned fallback. wry 0.57.2 registers no `ProcessFailed` handler; recheck the resolved version. [Process-related events], [wry 0.57.2 source], [ICoreWebView2].
3. Classify unsuccessful `NavigationCompleted` events using `WebErrorStatus` and the navigation ID before choosing recovery. Cancellation and authentication challenges need different handling from failed app-page loads; do not treat every false `IsSuccess` as a reason to reload. Bound retries for approved app URLs. Route ordinary external links to the system browser, while preserving any explicitly approved authentication flow. [NavigationCompletedEventArgs], [WebviewWindowBuilder], [Opener plugin].
4. Offer a reload command handled by the app (menu item or shortcut) that runs from the native side, so it works when the page is blank or dead.
5. For a product shipping an embedded frontend, verify that release loads it: the page URL must be the app's custom-protocol origin (`useHttpsScheme` decides `http://tauri.localhost` or `https://tauri.localhost` on Windows), not `devUrl`. The Tauri CLI manages the `custom-protocol` Cargo feature; a manual build without it can retain development behavior. Check the actual features/build scripts and launch the shipped binary without the dev server. A product intentionally loading remote content needs its own explicit URL and offline-recovery contract. [Tauri configuration], [tauri crate features].

## Windows implementation notes

Version-specific integration notes for tauri 2.12.5, wry 0.57.2, webview2-com 0.39.1 and tauri-plugin-single-instance 2.5.5. The contracts below were checked against source and Microsoft documentation on 2026-11-15; they are not a compiled recovery implementation. Implement against the project's lockfile and verify in its installed package.

- **Return from callbacks before recovery UI.** WebView2 callbacks and COM access belong to the owning UI thread. Copy the needed event values there, enqueue recovery work and return; do not block the callback or open modal UI/a nested message loop. A worker may receive copied metadata and thread-safe Tauri handles and dispatch work back to the UI thread; never move the controller, event arguments or other raw COM interfaces to that worker. Calling `run_on_main_thread` from the UI thread is not a deferral guarantee: tauri-runtime-wry 2.12.3 executes same-thread messages immediately. Keep one recovery dialog open per incident and deduplicate browser-process failure reports by affected process group. Complete an IPC acknowledgement before starting the reload it permits. [WebView2 threading], [runtime lib.rs].
- **Unsuccessful is not always catastrophic.** Exclude `COREWEBVIEW2_WEB_ERROR_STATUS_OPERATION_CANCELED` from automatic recovery: an app refusal or superseding navigation can produce it. Authentication and proxy-authentication statuses can also be non-catastrophic; route them through the product's authentication policy instead of a reload loop. Correlate navigation IDs and document generations so a late result cannot replace a newer healthy page. Classify the remaining statuses and preserve the retry bound; do not bypass certificate errors as recovery. Whether every refused navigation emits cancellation was not tested. [NavigationCompletedEventArgs], [WebView2 error status].
- **Navigation allowlist.** Derive allowed app and development URLs from the actual config; allow the development origin only in a dev build. Compare parsed scheme, host and effective port for HTTP(S), not a prefix or scheme/host pair. Define explicit handling for custom protocols and any approved remote-authentication flow. Apply the policy to every WebView and its new-window path; an untrusted link must not turn an app WebView into a remote privileged page. [URL origin]
- **Where the reload command lives.** With a custom title bar and browser accelerators off, a dead page cannot offer its own reload. A surface that does not depend on the page is an item appended to the window's system menu (`GetSystemMenu` + `AppendMenuW`, handled as `WM_SYSCOMMAND` in a window subclass; use an id below `0xF000`, the range of Windows' own commands, with the low four bits zero, which Windows uses internally in `wParam`). It is reachable from the system menu and from the taskbar button.
- **Save before reloading a live page.** Use a correlated request with explicit saved/no-changes, failed and cancelled outcomes, validated against the actual caller and document/session generation. Reload only after successful durable save, confirmed absence of dirty state, or the user's explicit discard choice. A timeout means the outcome is unknown: retain the page and offer wait/retry/cancel or explicit forced recovery. It does not prove the renderer is dead or authorize discarding a slow/failed save. Ignore late acknowledgements from an older document. A confirmed renderer exit follows crash recovery with persisted drafts; a timeout alone follows the live-page contract.
- **What the native side must know without the page.** Recovery dialogs and the menu item appear exactly when the page cannot draw: if the app is localized or themed, persist the language and the theme where the native side reads them.
- **Restart after a browser-process exit.** `AppHandle::request_restart()` runs `cleanup_before_exit`; tauri-plugin-single-instance 2.5.5 releases its lock there. A direct `std::process::exit` skips that cleanup. Tauri's `process::restart` spawns the new process before the old one exits, so app-owned file locks or ports still need a bounded reacquisition/retry contract. Persist state before restarting and verify the replacement instance actually opens. Avoid adding runtime environment mutations as a synchronization mechanism. [single-instance lib.rs], [process.rs].
- **A normal exit is not a failure.** Closing the app ends its WebView2 processes too: check that no recovery surface appears then.

## Own the native registrations

This is an installation contract, not a drop-in COM snippet. A short function that discards registration tokens cannot provide retry, rollback and teardown correctly for every application's lifecycle.

1. **Create one owner per actual WebView instance.** Keep its controller/core interfaces, separate event tokens and installation state on the owning UI thread. Key identity by instance/generation, not only the reusable window label. Share environment-level `BrowserProcessExited` registration across that environment's controls. Repeated bootstrap for an installed instance must be a no-op; a rebuilt instance gets new registrations.
2. **Install transactionally.** Register `ProcessFailed` and `NavigationCompleted` with distinct tokens. Retain each token as soon as its call succeeds. If a later registration or required setting fails, remove every subscription added by this attempt and report both the original error and any rollback errors. Do not erase tokens for removals that failed. Disable the engine error page only when the app-owned fallback is ready; retain the previous setting if a failed installation needs to restore it. [ICoreWebView2], [ICoreWebView2Settings].
3. **Record the actual result.** Handle both the outer `with_webview` dispatch result and the installation result inside its callback. Report the WebView label, generation, operation and COM error to the application's diagnostics. Scheduling success is not installation success. A failed or partly rolled-back instance stays marked failed; repair/tear it down before trying a new installation, rather than adding duplicate handlers blindly.
4. **Keep handlers small and accountable.** Read event kind/status, navigation ID and the needed frame/process metadata on the UI thread; enqueue copied values with the instance generation. Report COM-read and enqueue failures. Recovery workers never retain event arguments or controller interfaces. Check the shutdown/closing state before presenting UI, and reject stale work for a disposed generation.
5. **Remove before disposal.** On replacement or final destruction, remove both handlers on their owning thread using their saved tokens; attempt both removals even if the first fails. Remove the environment handler when its shared owner is no longer needed. Report errors and retain unresolved cleanup state until the controller/environment is conclusively closed; do not reuse it as a healthy installation. Define final UI-thread cleanup for every exit path. Test repeated install/remove, partial registration failure, reused labels and normal shutdown. Controller destruction is a final resource boundary, not a substitute for owned cleanup during a live controller's reconfiguration.

## Testing recovery on Windows without Task Manager

Use a disposable test instance with disposable application data and no unsaved user work. The following is a test design, not evidence that recovery works in a particular app.

1. Launch the intended built executable and retain its exact PID, start time and executable path. Give that child an isolated absolute WebView2 user-data folder (`WEBVIEW2_USER_DATA_FOLDER`, or the app's setting). If using CDP, enable a test-only debugging port through the child's environment, keep it local, and attach with a tool such as Playwright's `connectOverCDP`. Do not change a real profile or add debugging flags to shipped configuration. On Windows, launch background helpers with hidden windows.
2. Identify the test instance's WebView2 process group using the runtime's process information and the isolated data folder; verify process identity again immediately before termination. A command-line match is supporting evidence, not sufficient ownership by itself. Never terminate all `msedgewebview2.exe` processes or unrelated Edge/WebView2 instances. Distinguish the browser process from renderers and correlate the renderer with the target document/frame; a generic `--type=renderer` match does not identify the main frame.
3. Exercise one owned process at a time. A main-frame renderer exit should follow main-frame recovery; an out-of-process subframe exit should follow the frame policy. A browser-process exit should follow the affected-group rebuild/restart policy. Mark the document before the fault, then assert the new document generation, app-ready state and restored durable data. A missing marker alone does not prove a usable page. Reconnect automation after process/window replacement.
4. Inspect native recovery UI separately from DOM tests. Match windows to the owned test process and expected owner handle. For a known Win32 dialog, `EnumWindows`, class `#32770` and `IsWindowEnabled` can help verify modality; other native dialog implementations may need UI Automation. Invoke a verified control through the test harness; do not send an assumed `WM_COMMAND` to an arbitrary matching window.
5. Repeat through the configured retry bound and assert that one failure incident produces one recovery decision despite duplicate callbacks. Cover slow/failed saves, stale acknowledgements, authentication challenges and denied navigation. Finally close the app normally, verify no recovery UI appears, and stop only helpers owned by this test. Clean up its disposable data only after its processes have exited and its absolute paths are verified.

Other engines. macOS/iOS: WKWebView calls [`webViewWebContentProcessDidTerminate(_:)`] on its navigation delegate, and Tauri covers it. From 2.11.0 `Builder::on_web_content_process_terminate` registers a hook that receives the webview; with no hook, tauri-runtime-wry (checked in 2.11.4 and 2.12.3) reloads the webview by itself; the source shows no retry limit, and how that behaves under repeated crashes was not tested. Register the hook when the product needs the retry limit or an app-owned surface. Linux: WebKitGTK emits [`web-process-terminated`] "when the web process terminates abnormally"; neither wry 0.57.2 nor tauri 2.12.5 connects to it, so reaching it through `with_webview` is the app's job and is not verified. [app.rs], [runtime lib.rs].
